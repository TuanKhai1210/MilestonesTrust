01 / THE IDEA

Good intentions deserve
a better funding model.

Community teams need room to act. Sponsors need visibility. Independent auditors need a meaningful say in what happens next.

01 — REQUEST

A plan before a payment.

The team names the recipient, purpose and milestone. Everyone reviews the same request.

02 — REVIEW

Shared decisions.

A sponsor and a separate auditor approve independently. Change the request, and both must review again.

03 — VERIFY

Progress earns the next stage.

Delivery evidence gets reviewed before the next allocation opens. An open stage still needs a new request.

03 / INSIDE THE PROTOTYPE

A working flow.
Clear responsibilities.

The local application brings requests, reviews, mock releases and delivery evidence into one workspace.

APPLICATION

Rules enforced on the server.

The Next.js API checks membership, roles, independent reviewers and request versions. SQLite stores the campaign, approvals and mock payments.

View verification evidence →
IDENTITY & GOVERNANCE

A role for TideCloak.

The app integrates login and token verification. A configured Tide realm can govern protected identity changes through QEA. Live verification is the next integration step.

Read the integration plan →
Prototype scope and trust boundaries

All campaign records, identities in demo mode and funds are synthetic. QEA governs identity changes, not these payment records. The application server and SQLite remain trusted; the audit log is not immutable. Real bank integration, complete DPoP verification and live realm login/QEA are not demonstrated here.
